## 机制

`_rb_refine`（residual boundary search）在 V 的动态路径上做**有意非最近舍入**：
它用 kernel 从 V 回归出的近似注意力 `P` 求解 `min ‖P(target − best − correction)‖²`，
即把 V 的量化误差**投影到 P 的行空间之外**（推进 P 的零空间）。

```python
probability = _vk_probabilities(x, state, kh)[active]
if probability.shape[1] > 128:      # 128 = (qh/kh) * _VK_QUERIES * 4
    return params
```

其中 `_vk_probabilities` 只用

```python
ix = torch.linspace(0, x.shape[0] - 1, min(_VK_QUERIES, x.shape[0]))
```

**4 个 query 行**去估计 P。而校正能消除的误差维度受 `P` 的行数上界约束：
序列越长，`P` 的真实行空间维度（=T）越大，4 行估计严重低估可见子空间。

本版把 `_VK_QUERIES` 由 4 提到 **32**，并把 `_rb_refine` 的行数闸门由 128 相应抬到 1024。

## ⚠️ 必须报告的交付风险：动态开销

`_rb_factor` 的 Cholesky 是 **O(nrows³)**、`nrows = (qh/kh)·min(Q,T)·4`，**与 T 无关地以 Q³ 增长**。
实测每次动态 V 调用（5 case 合计）：

| 版本 | queries | 5-case 合计 | 折算 250 题（按公开库长度混合外推） | 相对 v504 |
|---|---|---|---|---|
| v504 | 4 | 0.402s | ~20s | — |
| v519 | 8 | 0.437s | ~22s | +2s |
| v520 | 16 | 1.246s | ~62s | +42s |
| **v521** | 32 | 1.591s | ~80s | **+59s** |
| v522 | 64 | 2.803s | ~140s | +120s |

用户回执的线上总耗时为 **261–269 秒**（v435/v440–v444），硬限 300 秒，
**只剩约 35 秒余量**。因此：

- **没有任何达到第 2 档的版本落在时间安全区内**（v520 需 +42s 但不达档，v521 需 +59s）；
- 上述外推依赖线上 250 题的序列长度分布。公开 mini-sample（`v419_mini_sample`）的
  长度为 10/128/512/1024/1，若线上相近则外推成立；若线上以短序列为主，增量会显著更小。
- 本机耗时不能直接换算鲲鹏线上耗时；这是量级提示，不是精确预测。

**建议**：提交时留意耗时。若线上耗时逼近 300 秒，可退到 **v519**（query=8，增量仅 +2s，
Δlocal +275.4，第 1 档更稳但不到第 2 档）。
