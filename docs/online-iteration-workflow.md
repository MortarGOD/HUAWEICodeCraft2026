# 线上反馈驱动的版本迭代（2026-09-07 用户授权）

每次收到用户提供的线上得分、耗时或错误结果，自动记录回执、核对提交源码及父版本、复盘预测偏差，并立即启动下一版本的研究和开发，无需再问是否继续。优先探索有条件落地的新优化策略；不要长期拘泥于参数微调、加轮数或等输出清理。当前优先 Linear，后续结合实际瓶颈和线上证据调整。

固定交付顺序：

1. 写实施计划，明确父版本及 hash、可证伪假设和替代解释，完成独立候选开发及必要机制检查。
2. 对独立提交文件运行 `self_check.py`，六接口与格式检查通过。
3. 直接提交并推送远端，保留父版本及默认入口；只提交本轮文件，不带入无关改动。用户已授权此步，无需重复确认。
4. 针对已经推送的确切源码运行本地数据集估计和回归，记录真实输出变化、负例、触发/回退和校准及动态耗时；报告原始结果与适用范围。
5. 将候选文件交用户上传竞赛平台。线上上传仍由用户进行；收到回执后自动进入下一轮。

本地估计不作为推送前置门槛，格式通过也不等于线上正确性、得分或总时限已获保证。当前 300 秒硬限、280 秒内部目标；不能可靠映射线上时就明确写尚不能可靠估分。若推送后验证发现问题，保留记录并主动修复、重跑格式检查、再次推送，再验实际文件；不隐瞒失败或撤销用户已有改动。

每 6 小时的 `test/base_1.7` 参考分支跟踪与此流程共同生效，已启动候选用版本号及 hash 对齐，避免重复开工。
