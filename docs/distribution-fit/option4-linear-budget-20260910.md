## 3. Linear 误差预算（`tools/probe_linear_budget.py`）

**方法**：纯评分端计算，不碰解法内部状态。
先前试图把精确权重/激活替换进解法自身输出，得到 −1012/−1436 的荒谬分数——
因为解法的激活量化是 **W-aware**（SmoothQuant 式耦合），单独替换一侧会破坏坐标一致性，
该反事实无效。故改为用评分端的标准 HiF4 计算两侧各自的可修池子。

**结果（50 例镜像库）**：

| 情形 | 每例得分 | 池子占比 |
|---|---|---|
| 基线（两侧标准 HiF4） | 0.0000 | 定义 |
| 激活换成精确、权重保持标准 | **+0.5367** | **53.6%** |
| 权重换成精确、激活保持标准 | **+0.4640** | **46.4%** |
| 两侧都精确 | 1.0000 | 自检通过 |

两池几乎**精确可加**（和 = 1.0007）。

**我们当前 0.7535/case**，即吃掉总池的 **75.35%**，剩余 **0.2465/case**
= 50 题合计 **+1232 分**的理论余额。

**注意**：openaddr 文档给的是「激活 77% + 权重 23%」与「完美权重天花板 75.7/case」，
与我们库上的 53.6/46.4 明显不同——**那是他们解法与判题数据上的数字，不可照搬**。
若按他们的数字，我们（75.35）已贴在完美权重天花板（75.7）上；但我们的库说权重端仍有 46.4% 的池子。

## 6. 失败记录：per-side 捕获率无法用简单重建得到

为定位"我们分别吃掉了两侧池子的多少"，试了两次反事实，**都无效**：

1. 直接把精确权重/激活替换进解法自身输出 → −1012 / −1436（激活量化是 W-aware，坐标不一致）。
2. 用最小二乘从解法权重参数反解逐通道缩放 `s`（`s_j = <Ŵ[:,j], W[:,j]>/<W[:,j],W[:,j]>`），
   再在原始坐标重建 `X̂ = act_params·s`、`Ŵ = weight_params/s` → **−303 / −8.6e8**。

原因：解法里还有 **Hadamard 旋转**（`_LINEAR_HADAMARD = 64`），参数处在旋转坐标中，
"除以对角 s"还原不出原始坐标。要得到有效的 per-side 反事实，必须走解法自身的输出函数
（例如其 `_linear_score_decode` 一类入口）并在同一旋转坐标内替换，而不是在原始坐标猜。

**因此本轮只确认了评分端的池子总量与两侧占比（有效），未确认我们的解法在两侧各自的捕获率。**

# Round 2 追加：池子全部集中在 M>K 的"宽"权重组，根因是 direct_output 路径的结构性门槛

## 1. 与 openaddr v43 的同库 A/B（50 例镜像库）

把 openaddr 的 `dist/solution_v43.zip` 解出来跑在我们的库上：

| 解法 | 前 3 组 | 全部 10 组 | 墙钟 |
|---|---|---|---|
| **我们 v435** | 0.824177 | **0.753340** | 37.3s |
| openaddr v43 | 0.743642 | 0.664349 | 26.6s |

**我们在全部 10 组都赢**（逐组 diff 全为正），所以他们的解法不是更好的机制来源。
但逐组画像暴露了真正的问题。

## 2. 关键发现：得分按权重形状分成两类

| group | W 形状 (M×K) | 我们 | openaddr |
|---|---|---|---|
| 1,2,3,5,8 | 1024×2048 / 512×2048（**M ≤ K**） | **0.9976–0.9998** | 0.87–0.97 |
| 0,4,6,7 | **2048×512**（M > K） | **0.4576–0.5390** | 0.28–0.45 |
| 9 | **2048×1024**（M > K） | 0.6016 | 0.4902 |

**完美分离：5 个 M≤K 组全部接近满分，5 个 M>K 组全部只有约 0.5。**

## 3. 池子不是形状差异造成的

按形状逐组做评分端预算，两侧池子在所有形状上**几乎相同**：

| group | 激活端 | 权重端 | ratio |
|---|---|---|---|
| 0 (2048×512) | 0.5412 | 0.4622 | 1.17 |
| 1 (1024×2048) | 0.5391 | 0.4621 | 1.17 |
| 7 (2048×512) | 0.5766 | 0.4214 | 1.37 |
| 9 (2048×1024) | 0.5399 | 0.4634 | 1.17 |
| **mean** | **0.5367** | **0.4640** | **1.16** |

→ **形状影响的是"我们捕获了多少"，不是"池子有多大"。**

我们捕获率：M≤K 组 ≈ **99.7%**；M>K 组 ≈ **47%**。
剩余池子 0.2465/case（50 题 +1232 分）**全部落在 5 个宽矩阵组**。

## 4. 根因：`direct_output` 残差阶段解码器只对 M ≤ K 开放

`solution_v435.py:2015`：

```python
if int(weight.shape[0]) < int(weight.shape[1]):      # M < K 才走直接输出路径
    slots, decoder_scale = _direct_output_layout(weight, activation_parts)
```

该路径（`_direct_output_layout` / `_direct_output_weight_params`）把载体当成**稀疏解码器**：
每个输出通道在 `slots[o, stage]` 放 `stages = max(1, K//M)` 个非零（值为 `decoder_scale`），
配合 direct_output 专用激活路径，得分 ~0.998。激活状态键也印证了两条路径的分叉：

- group 0（2048×512，M>K）→ `unrestricted_*`（GPTQ/变换族）
- group 1（1024×2048，M<K）→ `direct_output` / `target_weight` / `output_slots`

**门槛是结构性的，不是开关没打开**：`M > K` 时 `K//M = 0`，而载体只有 K 列，
每个输出通道连一个插槽都分不到，`slots` 会超出载体列数。要覆盖宽矩阵需要**新机制**，
不能靠放宽判据。

## 5. 下一轮的具体方向

宽矩阵（M > K）下输出维 M 大于输入维 K，激活通道装不下输出。
可探索：

1. **混合编码**：宽矩阵的部分输出通道走稀疏解码器、其余走高精度 GPTQ，按输出能量分配
   （`_direct_output_layout` 里已有 `extra_outputs` 的按能量分配先例可借鉴）。
2. **分块 direct_output**：把 M 个输出通道切成 ⌈M/K⌉ 块，每块独立做直接输出残差阶段。
3. 先做**诊断**：对宽矩阵组确认 GPTQ 路径到底卡在哪一环（权重端捕获 vs 激活端捕获），
   再决定投哪条。校准期的 Linear debug 字典当前为空，需要先加埋点。

## 6. 纪律

- 合成 iid 库对 Linear 有区分力、对 Attention 无（四版逐位相同），只可作**否决**。
- 线上超时 **300 秒**（用户确认）；提交目标 ≤280 秒。

# Round 3 追加：宽矩阵（M>K）的差距不是被关掉的开关，而是编码方式的缺失

## 1. 决定性对照：转置形状

镜像库里 **g1 = 1024×2048 得 0.9976，g9 = 2048×1024 得 0.6016**——两者是**互为转置**的同一维度对，
同一个库、同一批构造规则。仅转置就差 **0.40**。这排除了数据因素，坐实是**形状**决定成败。

## 2. 机制定位：direct_output 是一种"把输出编进激活通道"的编码

`_direct_output_weight_params` 把载体变成**稀疏解码器**：输出通道 o 在 `slots[o,stage]` 放
`stages = max(1, K//M)` 个非零。配合动态端的 `direct_output` 分支
（`solution_v435.py:2161-2191`），激活量化**直接把精确输出写进激活通道**：

```python
target = values @ target_weight.T          # 精确输出 (T, M)
for stage in range(stages):
    carrier.index_copy_(-1, local_slots, stage_residual / stage_scale)
    params = _quantize_linear_values(carrier, offsets=(-2..4))
    residual 减去已编码部分            # 多阶段残差逐级细化
```

即：**每个 stage 把 M 个输出值放进 M 个激活通道**，`stages*M ≤ K` 才放得下。
`M < K` ⇔ `stages ≥ 1`。这就是 2015 行判据的数学来源，也解释了 ~0.998 的来源：
输出被当作"码本"直接搬运，等效大幅提高输出精度。

**`M > K` 时 `K//M = 0`，激活只有 K 个通道而输出有 M 维，装不下** → 结构性不可用。

## 3. 宽矩阵并不缺信息，也不缺被关掉的搜索选项

宽矩阵路径**已经有** target-aware 激活量化（2203 行 `unrestricted_target_weight` →
`_quantize_linear_exact_target`，带 `unrestricted_block_gram/inverse`、`full_gram`）。
所以不是"没给精确 W"。

`linear_shape` 的能力分配（2094 行 `-1 if M<K else (1 if M>K else 0)`）：

| 形状 | `task_rounding` | `wide_candidates` | `extra_refinement` |
|---|---|---|---|
| M<K（高） | — | — | — （2015 行已提前返回，此分支到不了） |
| M==K（方） | ✅ | ✅ | ❌ |
| **M>K（宽）** | ❌ | ❌ | ❌ |

宽矩阵拿到最弱的一组能力，看上去像覆盖缺口。**实测否决**：

| 版本 | 改动 | 50 例镜像库 |
|---|---|---|
| v435 | 父版 | 0.753340 |
| v610 | 给宽矩阵开 `wide_candidates` | 0.752804（**−0.0005**） |
| v611 | 给宽矩阵开 `extra_refinement` | 0.753340（**恰好相同**） |
| v612 | 两者都开 | 0.752804（同 v610） |

（三者 self_check 均 22/22。）

## 4. 本轮结论

- 宽矩阵（M>K）组的差距**不是开关问题**，而是**编码方式的缺失**：tall 组靠 direct_output 的
  "输出搬进激活通道"拿到 0.998，而这一手法在 M>K 时数学上不成立。
- 评分端池子在宽/高两组上几乎相同（激活 ~0.54 / 权重 ~0.46），所以差距全在**我们的捕获率**：
  高组 ~99.7%，宽组 ~47%。
- **剩余 0.2465/case（50 题 +1232 分）集中在 5 个宽组，而其中可白拿的搜索选项已排除。**

## 5. 下一轮：需要新编码，而非调参

三条候选（按可行性排序）：

1. **M>K 的混合编码**：把输出通道按能量分成"载入激活通道的 K 个"与"走稠密量化的 M−K 个"，
   并让两部分共用同一组激活通道（需要设计正交/子空间划分，避免互相污染）。
   难度高，但这是唯一能复刻 direct_output 收益的思路。
2. **方形（M==K）的 direct_output 推广**：`K//M = 1` 时解码器退化为对角，
   理论上 1 个 stage 就能把一个 M 维输出全放进 K=M 个激活通道。当前判据是 `M < K` 而**排除了 M==K**。
   镜像库没有方形组，但线上可能存在——**这可能是最便宜的一口**，值得先做（改动小、风险低）。
3. 先把宽组的捕获率分解做实（当前中间张量抓取得到的参考坐标偏差与总误差同量级，只能算指示性）。

**方向 2 优先级最高**：判据 `M < K` 改成 `M <= K` 只影响方形矩阵，且若方形确实出现，
理论上能拿到与 tall 组同级的收益。

# Round 4 追加：宽组处在"补偿均衡"，且 direct_output 的方形推广被证伪

## 1. 有效的 per-side 分解（终于做对）

前两次反事实失败的原因是我在猜坐标。正确做法是用**解法自己在部署坐标里的理想量**：
`transformed`（激活的理想值）、`target_weight`（权重的理想值）、`deployed_weight`（实际部署权重），
它们都由 `hif4_dynamic_quantize_activation` 内部持有（`unrestricted_target_weight` 分支）。

一致性自检：`|transformed @ target_weight.T − X @ W.T| / |X @ W.T| = **0.0016–0.0017**`（0.17%）
→ 坐标自洽，分解有效。

| 组 | 总误差 | 激活端 | 权重端 |
|---|---|---|---|
| g0 (2048×512) t0 | 1.1628e-03 | 1.3868e-03（**119.3%**） | 1.1908e-03（**102.4%**） |
| g0 t1 | 1.1629e-03 | 1.4024e-03（120.6%） | 1.2869e-03（110.7%） |
| g9 (2048×1024) t0 | 2.0152e-03 | 2.9257e-03（145.2%） | 2.4261e-03（120.4%） |
| g4 (2048×512) t0 | 4.8401e-04 | 5.7207e-04（118.2%） | 5.3661e-04（110.9%） |

**两侧各占 100–145%，合计 >200%** → 两项误差**强反相关、正在互相抵消**。

换算成得分：g0 的基线 MSE ≈ 2.274e-3。
- 现状 0.49
- "我们的激活 + 精确权重"（即只剩权重端误差 e_w）→ 1.19e-3 → 得分 **0.389（比现状更差）**
- "精确激活 + 我们的权重"（只剩激活端 e_act）→ 1.39e-3 → 得分 0.389

**结论：单独修任何一侧都会更差。** 原因是 target-aware 激活量化本就拿着
`deployed_weight` 去优化（补偿权重误差），宽组已经处在**补偿均衡**上，瓶颈不在单侧。

## 2. direct_output 的方形推广（v613）被证伪

上一轮我提出：判据 `M<K` 排除了 `M==K`，而方形时 `stages = K//M = 1`，一级就够。
建了方形合成库（4 组 8 例：2048²/512²/1024²/768²）实测：

| 版本 | 方形合成库 |
|---|---|
| v435（走 GPTQ 路径） | **0.842135** |
| v613（开启 direct_output） | **0.625052（−0.217）** |

**原因：`stages = 1` 只有一级残差，精度太粗。** tall 组能到 0.998 靠的是
`stages ≥ 2`（1024×2048 → 2 级；512×2048 → 4 级）。所以原判据 `M < K` 是正确的，
我上一轮标记为"最便宜一口"的方向被自己的实验否掉。

**附带发现**：编码器的威力随 `stages = K//M` 增长，判据其实是"需要 `K ≥ 2M`"。
现有判据 `M < K` 会放行 `1 < K/M < 2`（stages=1，很可能同样差）的矩阵；
镜像库与已知线上样本（8192×2048）都没有这类形状，故无法本地验证。

## 3. Round 4 结论

- Linear 剩余池子（0.2465/case，50 题 +1232 分）**全部在宽矩阵组**；
- 宽组处在补偿均衡，**单侧修复会倒退**；
- 唯一已知的大杀器（direct_output 输出搬运编码）在 `M > K` 时数学上不成立
  （需要 `stages*M ≤ K`），方形推广也被实测否掉；

## 1. 更正：上一轮我对角色预算的读数说反了

`tools/probe_attention_role_budget.py` 打印的 `score(bm, vside)` / `score(bm, qkside)`
是**"只有该侧误差时的分数"**，而**"修好该侧之后的分数"是另一个量**：

```
修好 V   → 剩余误差 = Q/K 端误差 → score = score(bm, qkside)
修好 Q/K → 剩余误差 = V 端误差   → score = score(bm, vside)
```

正确读数：

| 库 | 现状 | 修好 V 后 | **V 端池子** | 修好 Q/K 后 | **Q/K 端池子** |
|---|---|---|---|---|---|

| public_quantizer（1 组 5 例） | 0.559 | **0.904** | **+0.345** | 0.658 | +0.099 |
| attention_history_fit_v1（5 组） | 0.388 | — | （V 归因 6.7e-4 vs Q/K 6.7e-4，接近对半） | — | — |

**修正结论：在我们全部库上，V 端既占当前残差的大头（78–87%），也持有多数池子（+0.34~0.44 vs +0.07~0.10）。**
我上一条消息称"Q/K 池子更大"是误读，特此更正。

这与 openaddr 的"判题器 Q/K 占 71–85%"**直接冲突**。本地无法分辨（拿不到判题器 attention 数据）。
